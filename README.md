# Continuous work

安装包为 `@local/continuous-work`，Host 与 Client 均通过包根入口加载，插件列表中英文显示名称统一为 Continuous work。保留原 `/codex-work` 命令、`codex_work` 工具及会话投影键，以兼容已保存的托管记录。

适用于各模型路由的额度恢复托管插件。根据统一额度错误码或明确的周期限额提示识别额度耗尽，等待恢复后自动重试，保留原会话、turn 和 step。托管开关在当前会话中持续生效，无总运行时限；每次对话最多等待 3 轮，可在设置中调整，新对话从零重新计数。底部以状态图标和固定标题 Continuous work 显示入口，点击打开信息页；通过“设置”进入独立参数页面。

## 安装

可直接从 GitHub 仓库安装，无需发布到 npm。把本仓库的 GitHub 地址交给 Harness Agent，并要求“安装这个 Harness 插件”；也可在插件管理器的外部安装入口填写仓库地址。正式部署建议使用带完整 commit 的 Git 安装地址，以便确定版本并支持管理器的 Git 更新路径。

如果从 GitHub Release 下载了 `.tgz`，让 Harness Agent 安装该文件的绝对路径即可。已经安装同名插件时，使用插件管理器的更新／替换流程。安装或更新会影响当前 profile 下的所有会话。

插件以包根入口加载 Host 和 Client，代码已可直接运行，不需要额外编译；安装器会处理 `zod` 依赖。`private: true` 仅阻止发布到 npm，不影响 GitHub 安装。运行结果以管理器返回的应用状态为准；宿主报告需要重启时再重启 Harness。

## 使用

1. 可直接使用当前模型，无需为托管功能切换路由。插件适用于各模型提供方，包括 Magpie、原生 OpenAI Codex 和 ZCode 等；是否等待恢复由实际错误中的额度证据决定。
2. 点击输入框下方带状态图标的 Continuous work 按钮启用托管；也可进入右上角“设置”页，调整单次对话最多允许的额度等待轮次。命令方式：

   ```text
   /codex-work start 3
   ```

   `3` 表示本次对话中最多安排三次额度等待，每次新对话重新计算。轮次接受正安全整数。托管开关会保持启用，直到手动停止；不设置总运行时限。同一次对话中关闭后重新开启，不会重置已用轮次。
3. 提交长任务。关闭浏览器可以，Harness 进程和机器需持续运行，网络需能恢复连接。
4. 正常对话的信息页显示状态与额度监测提示；等待额度时显示本次对话的等待进度和距下次尝试的倒计时。面板支持外部点击或 Escape 关闭，动画遵循减少动态效果偏好。
5. 运行中进入“设置”页修改轮次并点击“保存上限”，也可执行 `/codex-work update 3`。设置适用于后续等待；若调低到当前已用次数以下，本次对话不再安排新的托管等待，下一次对话从零开始。这里的轮次指额度等待次数，与 Goal 轮次无关。
6. 等待额度恢复时，若已手动恢复或重置额度，可点击“立即重试”，立即重试当前步骤。此操作保留会话、步骤和已有计数；若额度仍不足，且托管处于启用状态且本次对话仍有剩余等待轮次，才会继续自动等待。命令入口为 `/codex-work retry`。
7. “停止”只关闭托管，不主动取消当前执行。若当前已经处于额度等待，已安排的这次等待和随后对原步骤的尝试仍会完成，但停止后不会再安排新的托管等待。查询及停止也可使用：

   ```text
   /codex-work status
   /codex-work stop
   ```

模型可通过 `codex_work` 工具执行相同的操作。插件不改变权限策略或批准要求。

## 升级生效

本地插件链接中的版本号代表磁盘文件，后台仍可能保留旧模块。当前安装支持通过插件管理器重新启用已启用的条目，触发 linked package 及其依赖的后台热替换；应核对管理器返回的应用结果及运行中的工具定义。若宿主报告需要重启，再重启整个 Harness；仅刷新页面不会更新后台。前端会读取当前会话的实际命令能力；当后台仍为旧版时，暂时禁用所有托管操作并提示更新，以免调用旧版会取消执行的“停止”。

旧版本已经挂起的等待无法迁移到新模块。1.4.x 在卸载时会主动取消处于活动托管中的执行，升级前应等待相关会话的任务与额度等待结束；不要在运行任务时为了更新而关闭旧插件。新版会从会话记录恢复托管开关，原有开始／停止命令会保留其含义。

## 恢复策略

- 对任意路由识别统一错误码 `QUOTA`，或明确的周期限额提示（如 `usage_limit_reached`、ChatGPT usage limit、已达到小时上限）；认证错误不进入额度恢复，普通短时 429 由 Harness 原有重试处理。
- 优先使用 `providerRetryAfterMs` 并增加 5 秒余量。其次解析错误报文 JSON 中的 `resets_at`（Unix 秒，优先）或 `resets_in_seconds`，按提供方给出的重置时间增加 30 秒余量。绝对重置时间优先，避免代理重复返回旧报文时重新累加相对秒数。结构化字段只接受有限数值，且距当前时间不超过 6 小时；过期或非法字段回退到有界退避。
- 没有结构化重置字段时，保留近似分钟提示（增加 65 秒）和 ZCode 完整本地日期时间（增加 30 秒）解析；仅有 `before HH:MM UTC±H[:MM]` 时按明确时区偏移解析，支持跨午夜，仍限制为未来 6 小时内。缺少时区的时分提示不猜测。
- 无时间提示：1、2、4、8、16 分钟，之后每 30 分钟探测。每次实际安排额度等待计入当前对话的等待轮次，同一次等待被共享冷却延长不会额外计数。
- 同一插件进程内按失败请求的 `provider` 标识隔离冷却截止时间与错峰队列；同 provider 的不同会话共享冷却并计划错开 1 秒，不同 provider 互不延长等待。当前模型选择随后改变也不会改写原失败请求的归属。这不是严格的账户并发限流器，不区分同 provider 下的不同账户，也不跨进程共享。
- 如果 Codex 本身报告剩余约 3 小时，仍会按其重置时间等待；不会强制缩短为 1 分钟。修复的是等待时间来源及不同 provider 之间的串扰。
- 按会话中的 turn 计算等待轮次：等待安排时计数；重排同一次等待或立即重试不额外计数。新 turn 开始后重新从零计算；Goal 自动续轮也会创建新的 turn，因此也会重新计数。
- 当前 turn 达到配置上限后，插件不再安排新的托管等待，失败交还 Harness 原有处理。不会主动取消当前执行；若提供方仍报错，原有处理可能结束该 turn，也可能由其他已启用的重试策略继续处理。

## 连续性的边界

这是执行流程的连续性。服务端已经中断的单次生成会重新请求，插件不能恢复提供方没有暴露的隐藏推理或 KV cache。失败尝试由 Harness 保存为 `assistant/attempt`，不会派发其中未完成的工具调用；先前已完成工具由原执行循环保留。

等待轮次是插件在单个 turn 中安排额度等待的次数，不是套餐后台可验证的真实五小时窗口。当前适配层会将某些短时 429 也转换成同一限额提示，因此插件无法完全区分它们。周额度、认证错误及服务长期不可用仍可能阻止工作。

插件只处理已启用会话的请求失败，不会在正常最终答复后自行发送新输入。长任务若需要自动跨多轮推进，请使用 Harness 原有 Goal 功能；任务完成后可停止托管。当前版本不会自动给子 Agent 或其他会话启用托管。

同一步恢复要求进程存活。进程重启会丢失原来的 Promise／执行栈；插件不会伪装成同一步恢复，也不会补发“继续”之类的输入把任务重新拉起。托管开关从会话记录恢复，新对话使用新的等待计数。分叉会话不会继承父会话的托管授权。

## 数据与生命周期

状态由既有 `command/run`、`command/done`、`turn/start`、`llm/retry`、`llm/retry-started` 和 `turn/end` 事件增量投影，不写自定义 session 事件或会话提示。命令成功提交后才改变托管设置，并发修改按会话 reservation 拒绝。
