# Continuous work

安装包为 `@local/continuous-work`，Host 与 Client 均通过包根入口加载，插件列表中英文显示名称统一为 Continuous work。保留原 `/codex-work` 命令、`codex_work` 工具及会话投影键，以兼容已保存的托管记录。

适用于各模型路由的额度恢复托管插件。根据统一额度错误码或明确的周期限额提示识别额度耗尽，等待恢复后自动重试，保留原会话、turn 和 step。默认最多 3 个额度窗口、18 小时（含等待）。底部以状态图标和固定标题 Continuous work 显示入口，点击打开信息页；通过“设置”进入独立参数页面。窗口数与总时限可自定义，无 3 个窗口／24 小时的固定上限。

## 安装

可直接从 GitHub 仓库安装，无需发布到 npm。把本仓库的 GitHub 地址交给 Harness Agent，并要求“安装这个 Harness 插件”；也可在插件管理器的外部安装入口填写仓库地址。正式部署建议使用带完整 commit 的 Git 安装地址，以便确定版本并支持管理器的 Git 更新路径。

如果从 GitHub Release 下载了 `.tgz`，让 Harness Agent 安装该文件的绝对路径即可。已经安装同名插件时，使用插件管理器的更新／替换流程。安装或更新会影响当前 profile 下的所有会话。

插件以包根入口加载 Host 和 Client，代码已可直接运行，不需要额外编译；安装器会处理 `zod` 依赖。`private: true` 仅阻止发布到 npm，不影响 GitHub 安装。运行结果以管理器返回的应用状态为准；宿主报告需要重启时再重启 Harness。

## 使用

1. 可直接使用当前模型，无需为托管功能切换路由。插件适用于各模型提供方，包括 Magpie、原生 OpenAI Codex 和 ZCode 等；是否等待恢复由实际错误中的额度证据决定。
2. 点击输入框下方带状态图标的 Continuous work 按钮，可按默认参数启用托管；自定义参数请进入右上角“设置”页，输入额度窗口总数与总运行时限，点击“保存并启用”。也可执行：

   ```text
   /codex-work start 3 18
   ```

   表示当前额度周期加最多两次成功恢复，最长 18 小时（含等待）。窗口数接受正安全整数，小时数接受正有限数（可小数），可设置如 100 个窗口、72 小时；仅校验数值与日期可表示范围。重复启用会被拒绝，需要先停止。
3. 提交长任务。关闭浏览器可以，Harness 进程和机器需持续运行，网络需能恢复连接。
4. 底部图标用灰色表示未启用或已停止、绿色表示已就绪、蓝色动态标记表示工作或重试、黄色沙漏表示等待额度、红色感叹号表示中断或到达上限。正常对话的信息页只显示状态与额度监测提示，不显示恢复详情或倒计时；仅在实际等待额度或重试时展示窗口进度、成功恢复次数及重试次数。等待额度时显示距下次尝试的倒计时及时间点；恢复成功后自动隐藏。面板支持外部点击或 Escape 关闭，关闭按钮和 Escape 会把焦点交还图标；动画遵循减少动态效果偏好。
5. 运行中进入“设置”页修改两个参数并点击“保存上限”，立即更新当前托管，保留开始时间、窗口进度、重试次数和正在进行的等待。总时限从原开始时间计算；窗口数不得低于已用窗口数，等待恢复时还需保留下一窗口。也可执行 `/codex-work update 100 72`。开始与截止时间仅作为设置页的静态参数说明展示，不作为正常对话的信息页倒计时。这里的窗口是额度恢复周期，与对话轮次及 Goal 轮次无关。
6. 等待额度恢复时，若已手动恢复或重置额度，可点击“立即重试”，立即重试当前步骤。此操作保留会话、步骤和已有计数；若额度仍不足，将继续自动等待。命令入口为 `/codex-work retry`。
7. “停止”会取消当前托管和正在进行的执行。查询及停止也可使用：

   ```text
   /codex-work status
   /codex-work stop
   ```

模型可通过 `codex_work` 工具执行相同的操作。插件不改变权限策略或批准要求。

## 升级生效

本地插件链接中的版本号代表磁盘文件，后台仍可能保留旧模块。当前安装支持通过插件管理器重新启用已启用的条目，触发 linked package 及其依赖的后台热替换；应核对管理器返回的应用结果及运行中的工具定义。若宿主报告需要重启，再重启整个 Harness；仅刷新页面不会更新后台。若“立即重试”返回只包含 `start / status / stop` 的旧用法，说明后台仍为旧版本。前端会读取当前会话的实际命令能力，对旧后台禁用立即重试和设置更新，并显示重启提示。

旧版本已经挂起的等待无法迁移到新模块。重启后需从会话继续任务并重新启用托管，新版产生的额度等待支持立即重试。

## 恢复策略

- 对任意路由识别统一错误码 `QUOTA`，或明确的周期限额提示（如 `usage_limit_reached`、ChatGPT usage limit、已达到小时上限）；认证错误不进入额度恢复，普通短时 429 由 Harness 原有重试处理。
- 优先使用 `providerRetryAfterMs` 并增加 5 秒余量。其次解析错误报文 JSON 中的 `resets_at`（Unix 秒，优先）或 `resets_in_seconds`，按提供方给出的重置时间增加 30 秒余量。绝对重置时间优先，避免代理重复返回旧报文时重新累加相对秒数。结构化字段只接受有限数值，且距当前时间不超过 6 小时；过期或非法字段回退到有界退避。
- 没有结构化重置字段时，保留近似分钟提示（增加 65 秒）和 ZCode 完整本地日期时间（增加 30 秒）解析；仅有 `before HH:MM UTC±H[:MM]` 时按明确时区偏移解析，支持跨午夜，仍限制为未来 6 小时内。缺少时区的时分提示不猜测。
- 无时间提示：1、2、4、8、16 分钟，之后每 30 分钟探测。每次额度恢复最多 48 次失败后的重试，且始终受总截止时间约束。
- 同一插件进程内按失败请求的 `provider` 标识隔离冷却截止时间与错峰队列；同 provider 的不同会话共享冷却并计划错开 1 秒，不同 provider 互不延长等待。当前模型选择随后改变也不会改写原失败请求的归属。这不是严格的账户并发限流器，不区分同 provider 下的不同账户，也不跨进程共享。
- 如果 Codex 本身报告剩余约 3 小时，仍会按其重置时间等待；不会强制缩短为 1 分钟。修复的是等待时间来源及不同 provider 之间的串扰。
- 只有对应 turn/step 的成功回复才增加额度周期计数；取消、失败的部分回复和重排等待不会增加周期数。
- 达到用户配置的额度周期数、探测次数上限或运行截止时间时取消执行；取消信号确保通用 always-retry 策略不能重新启动该步骤。

## 连续性的边界

这是执行流程的连续性。服务端已经中断的单次生成会重新请求，插件不能恢复提供方没有暴露的隐藏推理或 KV cache。失败尝试由 Harness 保存为 `assistant/attempt`，不会派发其中未完成的工具调用；先前已完成工具由原执行循环保留。

额度周期是插件观察到的“限额后成功恢复”次数，不是套餐后台可验证的真实五小时窗口。当前适配层会将某些短时 429 也转换成同一限额提示，因此插件无法完全区分它们；有界退避可容纳这种情况，但计数可能与提供方的物理窗口不同。周额度、认证错误及服务长期不可用仍可能阻止工作。

插件只处理已启用会话的请求失败，不会在正常最终答复后自行发送新输入。长任务若需要自动跨多轮推进，请使用 Harness 原有 Goal 功能；任务完成后可停止托管。当前版本不会自动给子 Agent 或其他会话启用托管。

同一步恢复要求进程存活。进程重启会丢失原来的 Promise/执行栈；Harness 的中断 turn 结束记录使状态显示中断，插件不会伪装成同一步恢复，也不会补发"继续"之类的输入把任务重新拉起。正常结束但仍 armed 的会话在恢复后重建截止监控，等待下一次正常输入。分叉会话不会继承父会话的托管授权。

## 数据与生命周期

状态由既有 `command/run`、`command/done`、`llm/retry`、`llm/retry-started`、`assistant/message`、`turn/end` 事件增量投影，不写自定义 session 事件或会话提示。命令成功提交后建立取消与截止监控，并发修改按会话 reservation 拒绝。卸载取消并排空活动等待。
